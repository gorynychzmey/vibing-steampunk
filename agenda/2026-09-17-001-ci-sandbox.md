# A sandbox for the CI that cannot be tested where it will run

**Author:** vsp-ci
**Date:** 2026-09-17
**Status:** planned, nothing created
**Scope:** prove the `ci` branch's workflows on a throwaway public repo, then
land them on `vsp`.

## Why a sandbox at all

Three of the seven files on branch `ci` cannot be exercised from a pull
request, because `workflow_dispatch`, `workflow_run` and `issue_comment` all
read their definition from the **default branch**. A PR from `ci` runs exactly
one of them — `regression.yml` on `pull_request` — and even that produces no
comment, because stage two is not on `main` yet.

So the first merge into `vsp` would be partly blind. It is also the merge that
matters least to get right quickly: nothing here changes a line of Go.

A second reason, specific to this repo: 13 of the 14 open pull requests come
from forks. The whole two-stage design exists for that case, and a fork PR is
something a sandbox can produce on demand and `vsp` cannot.

## What must be proven

Four unknowns, in the order they block each other. Each has a pass condition
that can be read off the Actions tab without interpretation.

### 1. Does `gh workflow run` start a run when the token is `GITHUB_TOKEN`?

The open question in `command.yml`. GitHub suppresses events raised by
`GITHUB_TOKEN` to prevent recursive runs; whether `workflow_dispatch` is inside
or outside that rule is what this test settles.

- **Pass:** the comment gets 👀 then 🚀, *and* a new `Regression` run appears.
- **Fail:** both reactions land and no run appears. The `Command` job is green
  either way — that is the trap, and it is why the pass condition names the run
  and not the reactions.
- **Fix if it fails:** a fine-grained PAT with Actions: write in a secret, and
  `GH_TOKEN: ${{ secrets.DISPATCH_TOKEN }}` in the `env:` block of
  `command.yml`. One line.

### 2. Does the artifact survive the hop between workflows?

`regression-comment.yml` downloads by `run-id` with `github-token`. This is the
load-bearing join of the whole design.

- **Pass:** a comment headed "Regression test results" appears on the PR.
- **Fail modes to tell apart:** artifact not found (the download step is
  `continue-on-error`, so the job stays green and posts nothing — check the
  step log, not the job colour); `pr.txt` empty; comment posted but on the
  wrong issue number.

### 3. Does it work from an actual fork?

Not from a branch in the same repo. These are two different permission
regimes, and the branch case will pass even if the fork case is broken.

- Needs a second GitHub account or an org. Fork the sandbox, push a branch,
  open a PR.
- **Pass:** stage one runs with a read-only token and stage two still comments.
- **Watch for:** stage one trying to read a secret and failing silently.

### 4. `merge-green.yml` against messy input

The `statusCheckRollup` parsing is the part most likely to be wrong, and the
dry run makes it free to check.

Cases to stage deliberately: a PR with no checks at all; one with a check still
running; one with a skipped job; one conflicting; one draft. The verdict column
should name the reason in every row, and the run must merge nothing while
`apply` is unchecked.

## The sandbox repo

Public — a private repo burns metered minutes and the whole point is that this
costs nothing.

Minimum shape for `report.sh` to have something to measure:

- `go.mod`, module path anything.
- `cmd/<name>/main.go` — must build; binary size is one of the reported
  numbers.
- Two packages under `pkg/` with real tests, so coverage has somewhere to move.
  One of them deliberately under-tested, so a PR can raise coverage visibly.
- At least one benchmark with a knob that makes it measurably slower, so
  benchstat prints a difference rather than "~". Four benchmarks exist in `vsp`
  today and the section is thin; here it should be loud on purpose.

`report.sh` hardcodes `./pkg/...` and `BENCH_PKGS`. Either mirror those paths
in the sandbox or edit the two lines — mirroring is better, because it tests
the script as it will actually ship.

## Order of work

1. Create the repo, push the Go skeleton to `main`.
2. Copy `.github/` from branch `ci` and push **to `main`** — everything is
   inert until it lands there.
3. Enable Pages (Settings → Pages → Source = GitHub Actions) and confirm
   `coverage.yml` deploys.
4. Open a same-repo PR that changes coverage and slows a benchmark. Expect the
   comment. — proves (2).
5. Comment `/regression` on it. — proves (1).
6. Fork from a second account, open a PR. — proves (3).
7. Stage the five messy PRs and run `merge-green.yml` dry. — proves (4).
8. Try `/regression` from the second account on a PR it does not own: expect 😕
   and no run. The author-association guard is the one security control in
   `command.yml` and it deserves a test, not a reading.

## Then, on vsp

Merge `ci` into `main` with whatever the sandbox corrected. Separately, and
only with a decision:

- `allow_auto_merge` is `false` and `main` has no branch protection, so "green"
  currently carries no requirement and the merge button has nothing to wait
  for. Turning both on changes the rules for everyone sending a pull request —
  it is a repo-policy decision, not part of this branch.

## What this does not cover

`coverage.yml` needs a manual Pages setting on `vsp` too; a sandbox pass does
not carry over. And the sandbox proves the plumbing, not the thresholds: what
counts as an acceptable coverage drop or binary growth is a judgement nobody
has made yet, and none of these workflows enforce one — they report.
